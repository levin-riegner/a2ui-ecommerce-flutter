Snapshot: 14 October 2026, current local feature branch. Three agents independently analyzed catalog facts, component contracts, and real user journeys. This report is analysis; no application code, catalog, deployment, or Git publication changed for this request.

**The 977-product catalog is sufficient to activate most shopping and styling components.** The immediate work is host composition, action handlers, retained state, and more precise filtering. Another bulk import or vector database is not a prerequisite. Available product content does not establish sizes, stock, fit, delivery, or real checkout.

The companion [component library audit](/Users/kelvinharron/Developer/work/a2ui-ecommerce-flutter/docs/component-library-audit.md) inventories all 60 registered names and their current use. This report maps the actual products to those components and gives concrete flow triggers. A component being registered or demonstrated in the gallery is separate from being usable in the live journey.

## Recommended sequence

1. **Selection and recovery:** QuickAdjust, AlternativePiece, ThisOrThat and PicksStrip. Enforce strictly cheaper replacements, validate current IDs, retain selected pieces until acceptance, and distinguish exact garment requests from coarse categories. Keep the working budget recovery slider.
2. **Preferences and coverage:** ColourPicker with canonical colors and eligible counts; BrandPreferences with actual fictional catalog labels; owned-piece controls; accessory visuals; date-aware weather context. Distinguish soft preferences from hard exclusions.
3. **Completion and return:** dynamic Look/LookSummary, local saved looks and a clearly labelled demo bag. Add host persistence and handlers before offering controls.
4. **Evidence-backed integrations:** photo picking, mapping, product variants/size charts, stock, fulfillment and checkout. Only enable claims supported by those adapters.

Embrace the library through appropriate journey triggers. An initial shortlist needs ProductCard/PicksStrip; a two-item decision needs ThisOrThat; a completed outfit needs LookSummary. Showing every component at once would obscure the decisions the user is making.

## Confirmed gaps affecting recommendations

- **Exact garment relevance:** the actual offline runtime retained female styling and €500 after a dress selection, but Show jackets returned a vest and cardigan. Broad layer categorization is insufficient.
- **Formality relevance:** changing a blocked business outfit budget from €50 to €300 preserved its €45 shirt, then returned leggings/lounge shorts. Budget feasibility and audience compatibility do not establish business suitability.
- **Replacement price:** Cheaper currently stores preference text; a lower price must be enforced in search, fallback and final presentation. An equal-price jacket pair cannot be called cheaper.
- **Category visuals:** 166 accessories lack consistent finalized visuals; Look also invents placeholders for missing pieces and ignores owned/skipped slots. Nine coveralls occupy the one-piece/dress slot; that slot must not infer female styling.
- **Fact completeness:** 592 materials are unknown; all 21 bags have unknown material. No leather therefore excludes every bag under current conservative validation. Offer an owned bag or explicit restriction change, not a fabricated compliant product.

## Useful detail and missing detail

- Material is `unspecified` on 592 rows (60.6%), including all original 200. The remaining 385 contain 46 different labels. Some are broad surface/blend labels such as `textile`, `fabric`, `technical blend`, or `soft fleece`; these are not fibre composition guarantees. Exactly 18 unspecified-material products nevertheless have a fabric word in the name. Never turn a title such as Canvas Tote into a verified composition. Material-sensitive constraints cannot accept an unknown item as compliant.
- Colors contain 274 distinct descriptive strings; 25 records say exactly `multicolor`. This is enough to explain visible palette differences, but too many raw labels for a picker. There are no authoritative per-item hex swatches: parser defaults `Product.swatch` to `#e4e4e7` because the CSV has no swatch column. Any displayed hex for a palette family must be a UI approximation, not sampled photo color.
- Nine brands are fictional catalog labels: Alder Studio owns 777 rows; Quiet Meridian, Soft Current, Woven Orbit, Pale Lantern, Morrow Fold, Cloud Circuit, Fable Wardrobe, and Hearthline Studio have 25 each. The inventory supports real local preference filtering, but not genuine designer affinity, material quality, or vendor guarantees.
- There are 152 raw subcategory labels. 244 are only the seven broad category names. Singular/plural variants (`watch`/`watches`, `cardigan`/`cardigans`) need normalization for browsing chips. Some broad labels conflict with more specific prose: `demo-0511` is described as a crewneck tee but its subcategory is `cardigans`. Do not use raw subtype labels as exhaustive product truth without reconciling these examples.
- Seasons: 542 all-season, 195 autumn, 188 summer, 33 spring, 19 winter. Occasions: 624 weekend, 252 work, 52 travel, 49 celebration. These are inferred styling tags, not certification or suitability for every forecast. Layer includes 28 explicit robe subtype records: a layer slot alone cannot establish an outdoor coat. There are also nine coveralls subtype records in the dress slot, plus jumpsuits; user-facing labels should say one-piece where appropriate.
- Keywords support shape/visual explanations: common comma-delimited tags include relaxed (133), long sleeve (130), button front (125), sleeveless (100), minimal (95), collar (81), lace-up (80). Counts are exact comma-token matches, not standardized semantic counts; 33 records use space-based keywords and 944 comma-containing text. Additional normalization is needed before keyword-based controlled chips.
- No runtime Product fields exist for stock, sizes, variants, SKU, measured fit, composition percentage, delivery dates, shipping, merchant/source URL, enrichment confidence, waterproof or thermal rating. The ignored local enrichment workspace has source/reason artifacts, but they are not passed through the public Product model. Do not display fabricated availability, size suitability, rain protection, or checkout.

## Journey triggers and proposed rollout

### Batch 1: Make selection and recovery concrete

#### 1. A €500 women's dress look

Example: `demo-0092` Black Draped Wrap Dress, Pale Lantern, female, black, all-season, celebration, €230. The model can describe draping/short sleeves from stored text, but exact composition is unspecified. Present real ProductCards first. When the user specifically asks to compare two dresses, ThisOrThat can compare it with `demo-0135` Black Draped Sleeveless Mini Dress, female, black, all-season, celebration, €95. Explain silhouette and €135 difference using stored facts; selecting an option uses `select_product` with the exact ID.

ThisOrThat currently renders only two entries, despite its unrestricted list schema. Enforce exactly two. Use PicksStrip for three or more visual candidates, with ProductCards where price/description matter. Avoid silently truncating a larger shortlist. PicksStrip rows expect `productId`, while current host card data uses `id`; the host must adapt the shape explicitly.

When a filled slot is changed, show QuickAdjust. Its existing `adjust_piece` handler validates that the category is selected and preserves the old piece until a replacement is chosen. It currently treats Cheaper as preference text; it does not enforce a lower-than-selected price. Add a host replacement price ceiling of selected price minus €0.01, preserve all other pieces and hard restrictions, and validate replacement IDs before presenting them. The strict price cap must survive empty-search fallback and final presentation.

Verified eligible black female celebration alternatives below €230 include `demo-0198` Black Sheer-Panel Maxi Dress €55, `demo-0135` €95, `demo-0024` Rill Floral Slip Dress €110 (beige and black), `demo-0088` Black Strapless Midi Dress €155 and `demo-0075` €210. The current `black` filter is substring matching: the beige-and-black dress passes, so a picker must distinguish includes-black from exclusively-black semantics.

For an explicitly cold-weather jacket, source subtype/description as well as category. `demo-0089` Black Puffer Jacket with Brown Collar is shared-audience, winter, travel, €195; `demo-0187` Taupe Gathered Cropped Puffer Jacket is female, winter, weekend, €195. With the €230 dress, lowest-compatible shoes €45 and bag €95, that combination needs at least €565. An AlternativePiece for the €95 dress brings the arithmetic to €430. Declaring an owned bag instead brings it to €470. These are catalog arithmetic examples, not assurances of styling suitability or physical warmth.

An offline host probe with the actual CSV selected `demo-0092`, retained female styling and €500, then asked Show jackets. Results remained female/shared audience and within the available €270. However, the coarse layer search returned an Earth Beige Vest €45 and Black Tie-Hem Cardigan €50. The host currently enforces audience compatibility better than exact jacket intent. Do not label all layer candidates jackets or weather-protective pieces. Season/occasion are broadenable ranking/search facets, not all hard constraints.

#### 2. Business outfit at €50

Real `demo-0231` Cotton Shirt is shared-audience, cream, work, all-season, €45. Selecting it leaves €5. The real runtime emits BudgetSlider and PrimaryButton, reports minimum completion cost €225, and waits for an actionable correction. Enhance that recovery surface with AlternativePiece for a cheaper compatible selected item, a category choice for owned shoes/bag, and an explicit current budget label. Budget feasibility does not itself establish business appropriateness; ranking/intent rules must preserve the requested business context when optional filters broaden.

### Batch 2: Improve preferences, accessories and context

#### 3. Vague colour/brand preferences

Trigger ColourPicker when the person asks to explore colours or a broad shortlist needs palette clarification. Derive options and availability from the current compatible category and price ceiling, rather than the eight fixed gallery colours. Use liking colours as a soft ranking signal; only explicit Only/No instructions become required/excluded colours. The UI must disclose category scope before updating a global palette, and retain exact accepted values in host state.

Trigger BrandPreferences only when relevant brands have eligible products. The current inventory has Alder Studio on 777 rows and eight original brands on 25 rows each. Populate these actual labels, not the gallery's luxury defaults. `set_brand_preferences` is absent. Add a validated host handler for disjoint love/skip lists: skip maps to hard excludedBrands; love needs an explicit retained ranking preference rather than conversion to Only brand. Existing `preferenceScore` supports preferred colours, not a preferred-brand field.

Scarcity must drive the choices. There are only 21 bags, all shared audience. Only two blue bags exist: `demo-0034` slate blue €175 and `demo-0132` pale blue €230. No bag has a green, white, red or beige colour string; an olive bag `demo-0167` costs €195. Show unavailable/zero-count palette states and provide scoped relaxation or owned-category recovery. A global colour choice can prevent outfit completion even with abundant dress/layer options.

Every bag has material unspecified. A hard No leather instruction removes all 21 because the host cannot verify unknown materials. The actual host assessment reports bag unavailable. Do not loosen that silently, infer canvas from a name/photo, or promise a vegan bag. Offer keep restriction and own a bag, or an explicit restriction change. The whole catalog has 592 unknown materials, so material preferences cannot be presented as universally verified facts.

Accessories are optional, not required to make a look complete. Suggest a PicksStrip after core pieces are complete or on explicit request: `demo-0026` Tide Sculpted Drop Earrings female, gold, all-season, celebration, €25; `demo-0925` Khaki Cotton Scarf shared audience, khaki, all-season, travel, €25; `demo-0642` Pale Gray Dial Watch shared audience, work, €25. ## Shared host contracts for every rollout

- Explicit user audience, budget and scoped restrictions override model suggestions and inferred audience. Product styling labels are not the identity of a photographed wearer.
- Confirm accepted values in host prose and relevant controls; fields must reopen at retained values. UI edits remain drafts until one atomic submission.
- Every component event needs an allowlisted handler, validated context/IDs, epoch/surface freshness and inactive-history action isolation. Reuse existing selection/removal/budget handlers where contracts match.
- The host chooses components and supplies facts; the model can suggest presentation intent, eligible IDs and prose, but not invent component facts, pricing or available options.
- Search, fallback, presentation, selection and prospective completion apply the same hard constraints. Replacement retains the old item until an eligible choice is committed; errors/cancellation restore the prior state.
- Include factual metadata and recommendation reasons only when the corresponding catalog/source evidence exists. Warmth/formality are best-effort styling judgments, not physical measurements.

## Shared integration work

- Add typed host presentation intents (compare, alternatives, adjust, palette, brands, complete look) to the existing fixed producer rather than letting the model author arbitrary UI/facts. `renderStylistSurfaces` currently emits the same small vocabulary (`stylist_surfaces.dart:128`).
- Create one factual product-to-component row adapter with explicit aliases (`id` versus `productId`, `label`, numeric price versus display text). Components should share authoritative Product values and exact cents formatting; model output stays IDs plus styling advice.
- Add actions with host-owned state and rollback before emission. Existing dispatch supports refresh_city_context, find_options/update_budget, select_product, remove_product and adjust_piece; other gallery event names throw unsupportedAction (`stylist_runtime.dart:863–989`). Saving through model tool `save_outfit` updates current brief; it is not a persisted saved-look repository.
- Route every choice through current audience/constraint/budget/prospective-completion validation, including compact strips, swaps, weather add-ons, and stale saved-look restore. No new widget gets a weaker selection path than ProductCard.
- Keep display controls responsive to accepted user facts and corrections. State must distinguish retained audience provenance, preferred colours from required colours, Love from Skip, selected pieces from local bag contents, and owned pieces from products purchased in the demo.

## Targeted enrichment

Enrich specific decision fields rather than generating more prose: canonical colour families alongside original colour phrase; normalized subtype; visible garment length; visible silhouette/cut; formality as a declared demo classification; weather suitability as a clearly tentative styling label. Preserve source/evidence/confidence/unknowns per attribute and expose appropriate provenance in the public runtime model before making stronger claims. Source enrichment contracts already keep value/evidence/confidence (`tools/catalog/pipeline.py:280`), but Product/public CSV does not retain those details.

Do not use enrichment to invent composition percentages, available sizes, stock, waterproof ratings, technical warmth, measurements or delivery. Those require supplier/platform evidence. A vector datastore is not needed to adopt the existing components or perform deterministic price/audience filtering; it could improve semantic similarity later, without filling these factual gaps.
