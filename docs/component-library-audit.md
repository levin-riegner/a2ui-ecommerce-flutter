# Alder component library audit

Implementation follow-up (15 October): the table below preserves the original audit baseline. Subsequent local work adds recommendation guards, comparisons/replacements/preferences, accessory visuals, trip dates, completed looks, local saved looks and a demo bag. See [component-adoption-progress.md](component-adoption-progress.md) for current implementation and verification; baseline “gallery only” labels below are not the updated status.

Snapshot: 2026-10-14, local branch `feat/stylist-input-and-enriched-catalog`. Read-only implementation audit; the only repository addition is this report. Budget recovery and direct weather answers were being fixed concurrently, so they are included as current local code, not deployed behavior.

The library is substantially built. Adoption is incomplete: **60 registered names**, comprising **15 GenUI primitives and 45 custom names**, including **39 finalized Figma families** plus the host DressingRoom composition and five additional journey/screen components. The three design manifests include 40 entries because the right manifest also includes DressingRoom. **11 names are emitted by the current Genkit host**. Additional native/nested reuse includes UserMessage, ChatInput and PieceSlot; BagIcon appears natively but has no action and always shows zero.

A working renderer, a gallery action, a host-supported action and a service-backed feature are distinct states. The component and screen galleries demonstrate the first two. They do not establish live cart, saved-look, fit, photo or checkout behavior.

## Main gaps and concrete actions

1. **Host composition uses a small subset of the available vocabulary.** The model receives seven tools and retained facts, not exported component capabilities; it selects catalog IDs and writes prose. `renderStylistSurfaces` chooses the UI. Registering more renderers alone cannot make the model use them. Keep facts/actions host-authoritative and add explicit presentation intents/triggers for comparisons, palette clarification, replacement controls and completed looks.
2. **Most rich interaction contracts have no host handler.** Executing 19 representative events against the real offline StylistRuntime yielded `unsupportedAction` for every event, with zero model calls. This includes colours, size/fit, brand preferences, photos, timeline, saving/sharing/reloading looks, swapping, weather pieces, bag and venue map. Add handlers and state before displaying these as functional controls.
3. **The budget/weather complaint is a composition gap, not a missing widget.** BudgetSlider and TypicalWeather already exist. Current local fixes reopen budget controls on affordability recovery and produce direct, verified forecast answers. Generic budget editing still needs an explicit flow trigger. Weather is limited to five available forecast days; there is no structured trip date range in StylistBrief.
4. **The visible bag affordance is unfinished.** The native side rail has a `FinalizedBagIcon(count: 0)` without callback. Local demo cart persistence can unlock AddToBagButton, BagPreview, QuantityStepper and Toast without claiming real checkout. Inventory, variants, checkout and delivery still need adapter facts.
5. **Accessory support does not match the enriched seven-category catalog.** ProductCategory includes accessory, but shared LookTile/GarmentSilhouette schemas enumerate only six categories. Light FinalizedPieceSlot falls back to the old non-image primitive for accessories. Add an accessory glyph/schema/visual before adopting these for all products.
6. **Library adoption needs precise money, option and data contracts.** ThisOrThat silently truncates to two options although its schema allows a generic list. FinalizedBudgetSlider is continuous but labels whole euros. BagPreview/BudgetMeter round money to whole euros. QuickAdjust "Cheaper" currently records preference text without enforcing a lower-than-current price cap. Define these contracts before relying on them for financial recovery.
7. **There are two presentation implementations for overlapping names.** The original nine-item gallery uses CommerceProductCard/CommerceBudgetControl/CommerceDressingRoom, while current catalog registration replaces overlapping names with finalized renderers. The finalized gallery renders actual catalog schemas. Do not treat the old nine-widget gallery as visual proof of current A2UI production components; consolidate compatible examples/reuse gradually.

## Small implementation sequence

1. Finish budget recovery and direct forecast answers already under development; retain budget, selected products and gender across both actions.
2. Emit QuickAdjust after a filled-slot Change. Reuse existing `adjust_piece`; make Cheaper a real price cap and retain other pieces until a choice is confirmed. Add a clear Remove action.
3. Add optional ColourPicker and BrandPreferences with catalogue-derived options, authoritative constraint/ranking state and correction acknowledgment. No inventory service is required.
4. Add ThisOrThat for explicit two-product comparison and PicksStrip for compact alternatives. Use the same validated product IDs and `select_product` path as current cards. Do not broaden recommendations beyond current audience/constraints/budget.
5. Add LookSummary plus a local saved-look store and SavedLooksRail. Save brief, IDs and budget; validate product availability/constraints on restore. Share/reset can use native callbacks. This unlocks keep/save/swap behavior already promised by completion prose.
6. Add a clearly labelled local demo cart before rendering bag controls. Keep host-authoritative quantities, totals and undo. Bind BagIcon to actual count. Checkout should remain an honest demo handoff until a real adapter exists.
7. Add date/segment state for trips, then OccasionTimeline/DateTimeInput and a contextual weather response for the requested range. Use ContextStrip only for known facts; add real map links rather than placeholder map claims.
8. Add fit/size, photos and delivery only as their adapters become available. Preference collection can be local, but stock, fit guarantees, image analysis and arrival dates require separate evidence.

Every new active component should have a flow trigger, host action handler, retained state, validation, cancellation/rollback behavior, mobile/large-text behavior and a test for actual use. A component can remain an available compositional primitive until a user need calls for it.
